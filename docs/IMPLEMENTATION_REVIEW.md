# Сверка документации и реализации

За основу принята модель README.md: отдельный серверный TLS-сертификат,
регистрация по токену и CIDR, mTLS на управляющем порту, loopback-only выпуск
для клиентов и pull-only репликация. Описания push в DEPLOYMENT.md относились
к другой версии протокола и приведены в соответствие с этой моделью.

| Найденное расхождение | Исправление |
|---|---|
| Проект не собирался: отсутствовали `mtlsClient`, `ensureClientIdentity`, `ipsToStr`, `InstallRootCA`; старый вызов `RevokeCert` | Реализовано получение клиентского удостоверения, транспорт mTLS и преобразование IP; подключены существующие установщики доверия; унифицирован отзыв |
| TLS обслуживался ключом Root CA | Оба слушателя используют отдельный серверный leaf; корневой ключ используется для подписей |
| Pinning принимал любой набор сертификатов, содержащий нужный fingerprint | Проверяется цепочка серверного leaf до конкретного Root CA, назначение, имя узла и серверная идентичность |
| Публичный `/acme/new-order` выдавал произвольные сертификаты с приватным ключом | Обработчик удалён; произвольный выпуск доступен через CLI администратора |
| CSR отправлялся на 8443, где отсутствовал обработчик | Выпуск перенесён в mTLS control plane с проверкой регистрации, отзыва и блокировки на каждом запросе |
| Регистрация не выдавала удостоверение; пустой токен пропускал проверку | Клиент локально создаёт ключ и CSR; сервер выдаёт client-auth сертификат только после токена, CIDR и blacklist |
| Кэш и CRL принимались через открытые push-обработчики | Клиент получает их только по mTLS; входящий слушатель оставлен для подписанного уведомления о миграции |
| Версия кэша всегда равнялась 1, откат не проверялся | Разделены версия формата и последовательность; envelope подписан CA, последовательность сохраняется вместе с кэшем и в SQLite |
| CRL записывался без проверки на клиенте | Проверяются подпись, сроки и возрастающий номер; просроченный CRL обновляется сервером перед выдачей |
| Обычный сертификат выдавался на год вместо 90 дней | Установлены 90 дней; для localhost оставлен год, SAN ограничены loopback |
| Ошибки записи сертификата и ключа игнорировались | Ошибки возвращаются вызывающему коду; файлы заменяются атомарно с нужными правами; ошибка записи замены не отзывает рабочий сертификат |
| Миграция отправлялась, но не принималась; повтор пакета не ограничивался | Добавлен `/migrate`, проверка подписи, срока и сохранённой отметки предыдущей миграции |
| DR мог обращаться к пустому списку IP и записать CA до проверки fingerprint | Добавлены проверки адресов, seed, подписи кэша, пары ключ/сертификат и fingerprint до записи; восстановлены политика регистрации и счётчики |
| `make test` требовал race detector при отключённом CGO | CGO включён для race-тестов; обычная и кроссплатформенные сборки остаются pure-Go; тесты включены в CI |

Снимок состояния собирается в транзакции SQLite. Публикация кэша защищена
файловой блокировкой между процессами; выпуск и перевыпуск одного имени
также сериализованы между CLI-процессами; последовательность не откатывается при
перезапуске и восстановлении. Изменения администратора сразу публикуют новый
снимок; клиент получает его при следующем `pull_interval`.

## Проверки

- `make ci`: `go mod tidy` без изменений go.mod/go.sum, vet, race-тесты,
  Linux amd64/arm64 сборки.
- 18 верхнеуровневых тестов и 4 дополнительных сценария регистрации:
  настоящие TLS/mTLS-соединения, выпуск/отзыв/блокировка, защита pinning,
  подмена и откат кэша/CRL, шифрование ключей, конкурентная публикация,
  обработчик миграции, сохранение состояния при недоступном master,
  восстановление через производственный код DR и совместимое обновление
  старого неподписанного кэша.
- Запуск бинарника: bootstrap, выпуск, проверка цепочки и SAN через OpenSSL,
  перевыпуск, отзыв, HTTPS health/CA с проверкой имени и доверия, отказ без
  mTLS-удостоверения, повторный запуск master.
- Релизные сборки Linux и Darwin для amd64/arm64.

## Эксплуатационные границы

Master и клиенты требуют согласованного обновления протокола. Старый
неподписанный кэш разрешено заменить новым подписанным снимком, но нельзя
использовать для DR. Перед тем как полагаться на восстановление, нужна успешная
синхронизация после обновления.

TCP/ICMP/ARP-проверки не отличают падение master от сетевого разделения.
Перед promotion старый master должен быть изолирован оператором. Реальные
межмашинные ICMP/ARP, systemd, Docker и установка доверия ОС/Firefox требуют
проверки на целевом дистрибутиве; локальные тесты не меняют системное доверие.
Для миграции используются стандартные порты; дополнительные адреса управляющего
API предназначены в том числе для локального тестирования.
